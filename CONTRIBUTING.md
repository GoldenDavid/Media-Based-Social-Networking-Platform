# Contributing

Welcome! This document covers the day-to-day conventions for contributing
to the Media-Based Social Networking Platform.

> **Before you start**, read [`README.md`](README.md),
> [`architecture.md`](architecture.md), and
> [`docs/DECISIONS.md`](docs/DECISIONS.md). Most "how do I …?" questions
> are answered there. Anything that requires a deviation from a locked
> decision needs a new ADR — see "PR process" below.

---

## Code style

Style is enforced by the Gradle / ESLint configs at the root of each
module. The local formatters and linters match those rules, so you rarely
need to think about it — but for the cases where you do:

| Language / file type | Indent | Line length | Other |
|----------------------|--------|-------------|-------|
| **Java**             | 4 spaces | 120         | Spring Boot 3 / Java 17 idioms. No `*` imports. Javadoc on every public type in `socialnetwork-common`. |
| **TypeScript / JSX** | 2 spaces | 100         | ESLint + Prettier config in `frontend/`. No default exports for components. |
| **YAML**             | 2 spaces | —           | One space after `:`, no trailing whitespace, files end with a newline. |
| **Markdown**         | 2 spaces (lists) | —      | One H1 per file. Reference docs / ADRs / CHANGELOG are sentence-case titles, not Title Case. |
| **Groovy (`*.gradle`)** | 4 spaces | —        | One `dependencies { }` block per concern. |
| **Protobuf**         | 2 spaces | —           | One `service` block per file. Never remove a field without a deprecation cycle — see "API contracts" below. |

If you are adding a Java service, follow the layout of the existing
modules (`profile-service/`, `post-service/`, etc.):

- `src/main/java/com/socialnetwork/<service>/`
  - `config/`     — `*Config` beans (security, session, gRPC client, queues)
  - `controller/` — REST controllers
  - `dto/`        — request / response DTOs
  - `entity/`     — JPA entities
  - `repository/` — Spring Data repositories
  - `service/`    — business logic
  - `grpc/`       — gRPC clients (if any)

## Branch naming

Branches follow a `<type>/<scope>` convention. The `scope` is short and
lower-kebab-case.

| Type       | When to use                                   | Example                          |
|------------|-----------------------------------------------|----------------------------------|
| `feature/` | New functionality                             | `feature/phase-2-redis-session`  |
| `fix/`     | Bug fix                                       | `fix/feed-pagination-off-by-one` |
| `chore/`   | Repo hygiene (deps, CI, docs)                 | `chore/bump-spring-boot-3.2`     |
| `refactor/`| No-behavior-change code cleanup               | `refactor/post-service-dtos`     |
| `docs/`    | Documentation-only change                     | `docs/adr-013-shared-session`    |

For multi-lane refactors (e.g. the Phase 1 work split across four
parallel agents), append the lane: `feature/phase-1-lane-a`,
`feature/phase-1-lane-b`, etc. Each lane works in its own worktree and
opens a PR back to `main`.

## Commit messages

Single-line summary in the imperative mood, prefixed with a
`<lane|scope>:` tag. The scope is the module, service, or topic area.

```
<scope>: <imperative summary>

<optional body — explain the why, not the what>

<optional footer — references to issues / ADRs>
```

Examples:

```
profile-service: switch to shared UserPrincipal (ADR-013)
frontend: proxy /api and send credentials (ADR-014)
docs: add architecture diagram and CONTRIBUTING guide
seed: include follow graph for the dynamic feed demo
infra: fix docker-compose port for media-service
```

Rules:

- Subject line ≤ 72 characters, no trailing period.
- Use the present tense: "add", not "added".
- One logical change per commit. If you find yourself writing "and" in
  the subject, split the commit.
- Reference an ADR in the body when your change enforces or modifies a
  locked decision: `Refs ADR-013.`
- Do **not** include "Generated by …" or "Co-authored-by: …" trailers
  unless they add real signal.

## Pull request process

1. **Branch off `main`.** PRs are merged back into `main`. The
   `feature/phase-*` long-lived branches are cut from `main`, not from
   each other.
2. **Open the PR as a draft** while you are still iterating. Mark it
   "Ready for review" when:
   - All commits follow the conventions above.
   - `./gradlew build -x test` succeeds locally (Lane A owns the build).
   - The frontend lints (`cd frontend && npm run lint`).
   - New / changed behavior has at least one test, or a written
     rationale for why a test is not feasible (e.g. requires a
     long-running RabbitMQ container).
3. **Link an ADR** in the PR description if the change is
   architectural. A new ADR is a separate PR against
   `docs/DECISIONS.md`; the implementation PR references it.
4. **CI must be green** before review. The CI job runs
   `./gradlew build -x test` + `npm run build` + a `docker compose up`
   smoke test.
5. **Reviewers**: at least one approving review from a code owner of
   the affected module. Cross-cutting changes (gateway, session,
   queues) need a review from the owner of each touched module.
6. **Squash-merge** by default. The squash commit message is rewritten
   to follow the conventions above.
7. **Delete the branch** once the PR is merged (the remote will warn
   you; the worktree lives on in your local clone if you need it).

## API contracts

- **HTTP / JSON.** Every REST controller returns a `BaseResponse<T>`
  envelope (or a feed-specific response — see
  [ADR-002](docs/DECISIONS.md)). New endpoints must use typed DTOs, not
  `Map.of`. Frontend types are generated from `springdoc` OpenAPI —
  after adding or changing a response, run the codegen in
  `frontend/` and commit the regenerated `src/types/api.d.ts`.
- **gRPC.** A change to a `.proto` file in `proto-contracts/` is a
  breaking change for every consumer. Coordinate the proto change
  with all services in a single PR, or use a deprecation cycle
  (mark the field `[deprecated = true]`, ship a new field, remove
  the old one later).
- **RabbitMQ.** Adding / renaming / removing a queue **must** update
  [`docs/queues.md`](docs/queues.md) in the same PR. The same goes for
  any new exchange or binding.
- **Redis keys.** A new key prefix requires an entry in
  [`docs/DECISIONS.md`](docs/DECISIONS.md) (or an ADR amendment) so we
  do not collide with the shared session namespace
  (`engineerpro:app`).

## Local checks before pushing

A short checklist that catches the most common CI failures:

```bash
# 1. Build (skip tests — Lane A owns test maintenance)
./gradlew build -x test

# 2. Frontend lint + build
cd frontend && npm run lint && npm run build && cd ..

# 3. Validate docker-compose (catches bad YAML / missing env vars)
docker compose config

# 4. Mermaid — if you touched a *.md file with a ```mermaid block
#    Paste the block into https://mermaid.live to confirm it renders.
```

If you changed queues, gRPC, or session config, also do a quick smoke
test against the running stack:

```bash
docker compose up -d
curl -s http://localhost:8080/actuator/health
docker exec -it rabbitmq rabbitmqctl list_queues name messages consumers
```

## Questions?

- Look in [`docs/`](docs/) first — it is the canonical home for
  architectural and operational answers.
- Open a `docs/` PR to update the docs you wish existed.
- For everything else, file an issue with the `question` label.
